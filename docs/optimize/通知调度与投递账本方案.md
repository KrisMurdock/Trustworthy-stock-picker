# 通知调度与投递账本方案

核对基线：`33ab655`，2026-10-29。本文记录当前源码的调度与持久化规则；真实通道权限和部署状态须另行验证。

## S｜情境：同一进程有四套通知执行器

报告发布、实时预测、盘前区间和盘前执行卡各自管理发送时机，共用 [notify.Ledger](../../internal/notify/notify.go) 状态模型。账本保存待发正文与通道状态，进程重启后可以继续发送；微信公众号的 `delivered` 只表示草稿创建成功。

当前实现不能承诺“恰好一次”：上游已接收、进程却没能保存确认时，重启后可能重发。事件去重保护的是本地账本，不是飞书或微信的远端内容。

### 入口与持久化位置

以下路径均相对配置中的 `data_dir`，四个 JSON 文件的 schema 都是 2。

| 账本 | 所有者 | 承载内容 |
| --- | --- | --- |
| `state/delivery.json` | [monitor](../../internal/monitor/monitor.go) | 正式推荐、详情、初筛、精排、初筛回看 |
| `state/predictor-delivery.json` | [predictor.Monitor](../../internal/predictor/monitor.go) | 实时预测及实际结果卡 |
| `state/dayrange-delivery.json` | [dayrange delivery](../../internal/dayrange/delivery.go) | 盘前区间分页卡和公众号盘前文章 |
| `state/premarket-execution-delivery.json` | [dayrange execution](../../internal/dayrange/execution.go) | 精排与冻结盘前预测合成的执行卡 |

`status` 与 `retry [channel]` 的 CLI 分支只调用主 `monitor`，因此只操作 `state/delivery.json`。不能据此认为其余三份账本已被查看或解锁。

## T｜任务：先保存发送意图，再进入外部通道

| 责任 | 契约 |
| --- | --- |
| 报告转换层 | 生成 `Message`、稳定事件 ID、过期时间及分页关系，不发送 HTTP |
| `Ledger` | 校验 schema、按事件保存正文、维护每个通道的独立状态 |
| 执行器 | 读取账本、检查时间和依赖、持久化 `in_flight`、调用通道、保存结果 |
| `Channel` | 实现 `Name()` 与 `Send(context.Context, Message) error` |
| `Store` | 单写所有权、共享盘检查、JSON 原子替换与严格读取 |

`Message.Version` 支持 1、2；不能把它与账本 schema 2 混为一个版本。`Event` 保存 `as_of`、`expires_at`、`part`、`sequence`、`depends_on`、完整 `message` 与 `channels`。每个通道记录状态、错误类别、失败次数、下一次尝试时间及可能重复标记。

配置路由在 [config.go](../../internal/config/config.go) 定义：`selection`、`first_stage`、`second_stage`、`premarket_execution`、`predictor_realtime`、`predictor_dayrange`、`wechat_premarket` 和 `all`。配置匹配支持逗号分隔；具体执行器仍有自己的通道筛选实现，不能假设所有消费者使用完全相同的匹配逻辑。

## A｜行动：入队、发送与恢复

### 1. 日常调度的先后顺序

[prepareStartup](../../internal/monitor/startup.go) 先加载账本，再刷新完整股池，并确认刷新前后的已完成交易日一致。成功后准备精排并入队；启动刷新失败时不会用缓存推荐进入正常发送循环。启动成功后，投递失败由后续轮询重试，不重新下载整池。

`Cycle` 先刷新已有到期投递，再判断 `daily.run_at` 是否到期。到期且缺报告才同步，已有报告则检查目标交易日，随后准备精排、入队本轮卡片、尝试入队初筛回看，最后再刷新投递。初筛回看入队失败只记警告，不覆盖其他步骤的结果。

日常推荐和盘前文章有效至目标交易日北京时间 09:30；实时预测卡的截止时间是目标 bar 结束时间。各类卡片由生产者设置 `ExpiresAt`，执行器不替所有消息规定同一个有效期。

### 2. 去重分为两层

`Ledger.EnqueuePart` 以 `Message.EventID` 为键。已有事件必须保持相同 `as_of` 和消息 ID；函数仅补入缺少的通道，保留已有正文、状态和依赖信息。它不会比较新旧全文，也不会用新正文覆盖同 ID 的旧消息。

主报告入队还有更宽的保护：[pendingChannelNames](../../internal/monitor/startup.go) 检查同一数据日期、同一通道是否已经出现在任意事件中。只要存在记录，就不为刷新后的报告重新入队该通道；此检查不区分 `pending`、`blocked`、`unknown` 或 `delivered`，也不以事件类型作为额外去重键。

因此，同日刷新可生成新报告 revision，但不代表同日通知会重发。初筛回看走独立事件检查，不能套用主报告入队的日期保护解释所有消息。

| 消息族 | 当前事件 ID 形态 |
| --- | --- |
| 主卡、详情 | `<report ID>:main`、`<report ID>:detail:<页号>` |
| 初筛回看 | `first-stage-review:<信号日>:<评价日>` |
| 实时预测、实际结果 | `intraday:<日期>:<目标结束 Unix 秒>`，实际结果加 `:actual` |
| 盘前区间分页 | `dayrange:premarket:<目标日>:<页号>` |
| 公众号盘前文章 | `dayrange:premarket-article:<目标日>` |
| 盘前执行卡 | `premarket-execution:<目标日>` |

事件键是各生产者的设计，不是账本从标题或正文自动计算出的通用内容哈希。删除账本会丢失这层去重依据。

### 3. 状态机与退避

| 触发 | 新状态 | 其他字段与后果 |
| --- | --- | --- |
| 新事件增加通道 | `pending` | 尚未尝试 |
| 发送前持久化 | `in_flight` | 记录 `InFlightAt` |
| 通道返回成功 | `delivered` | 清除错误类别、下次尝试时间和飞行时间 |
| `MarkFailure(permanent)` | `blocked` | 失败次数加一，无自动下一次尝试 |
| `MarkFailure(retryable/unknown)` | `pending` | 失败次数加一，设置退避；错误类别仍可为 `unknown` |
| `MarkUnknown` 或恢复遗留 `in_flight` | `unknown` | 设置 `PossiblyDuplicate=true`，不增加失败次数 |
| 到期且尚未成功 | `expired` | 清除重试与飞行时间 |
| 对未过期 `blocked` 调用 `Retry` | `pending` | 清除错误类别与重试时间，保留已有失败次数 |

`unknown` 有两种语义位置：它可以是 `ChannelState.Status`，也可以只是 `Kind`。普通未知错误经 `MarkFailure` 后，状态为 `pending`；只有恢复发送中记录或显式 `MarkUnknown` 才把状态设成 `unknown`。

`Due(now)` 同时选择到期可试的 `pending` 和 `unknown`，且要求消息未过期。`unknown` 不等待人工许可。失败退避为 `2^min(Attempts,8)` 分钟，即首次失败 2 分钟，上限 256 分钟；通道返回更长 `RetryAfter` 时采用更长等待。

`Retry` 只解锁未过期的 `blocked`，没有匹配项就返回错误。它不会重发已送达消息，不清空失败次数，也不核对远端是否已经收到。

### 4. 分页依赖与排序

`Due` 先按 `as_of`、`sequence`、事件 ID 排序，再按通道名排序；它本身不检查依赖。执行器调用 `CanDeliver`，要求前置事件在同一通道已经 `delivered`。

正式推荐详情依次依赖主卡和上一页；初筛、精排各有自己的页链，不要求先收到正式推荐主卡。盘前区间也按页链发送。前页失败只阻止该通道的后页，不阻止另一通道已满足条件的页面。

终态包括 `delivered`、`blocked`、`expired`。清理阈值从事件 `ExpiresAt` 起算 30 天；如果仍有非终态子事件依赖它，就保留前置事件。不能按“最后发送时间过去 30 天”解释清理规则。

### 5. 四套执行器的差异

| 情况 | 主 `monitor` | 实时预测、盘前区间、盘前执行卡 |
| --- | --- | --- |
| 单次发送 context | 父 context 与消息剩余有效期共同约束 | 再加最多 10 秒的发送期限 |
| 通道不在运行集合 | 跳过，保留原状态等待后续 | 标记永久错误 `channel_missing` |
| 已分类错误 | `errors.As` 解包 `DeliveryError` | 只识别直接的 `*notify.DeliveryError` |
| 未分类错误 | `Kind=unknown`，退避为 `pending` | `Kind=retryable`、`send_failed`，退避为 `pending` |
| `Send` 返回错误且发送 context 已取消/截止 | 标记可能重复；父 context 取消保留 `unknown`，仅消息期限耗尽则过期 | 普通错误处理，通常回到 `pending` 退避 |

若 `Send` 返回 nil，主 monitor 即使此时 context 已结束也先保存 `delivered`，再返回父 context 错误；上表的 unknown 分支不能只看 context 状态判断。

微信 API 业务错误外面包着 `apiError`。主 `monitor` 能解包其中的永久错误；盘前文章使用的 dayrange 执行器只做直接类型断言，因此这类包装错误当前会被归为 `send_failed` 重试。此处是现有行为差异，不能在文档中写成所有路由都可靠区分永久业务码。

禁用推送也有差异：实时预测主动把 `pending/in_flight/unknown` 过期；dayrange 关闭 `PushEnabled` 后只对已到时间的事件执行过期，不立即丢弃全部待发事件。

### 6. 崩溃和共享盘故障

正常发送顺序为：检查共享盘、保存 `in_flight`、重新计算剩余有效期、调用通道、保存结果。共享盘写入本身可能耗时，剩余时间检查发生在保存之后，避免把已经过期的消息发出去。

`Store.Write` 以临时文件、文件同步、重命名和目录同步替换账本；调用过程中再次确认共享盘。成功 HTTP 和账本写入不在同一事务内。若远端成功而本地结果保存失败，磁盘可能仍是 `in_flight`，重启规范化后成为可重试的 `unknown`。

只读 `status` 不恢复发送中状态、不迁移写入。主账本的写拥有者可以迁移旧 schema 1；其他三份账本只接受 schema 2。损坏 JSON 或不支持的版本返回错误，不当作空账本覆盖。

### 7. 排障顺序

1. 先确定消息属于哪份账本和哪条路由，记录事件 ID、通道、状态与过期时间。
2. 检查是否被同日期通道去重、前页依赖、推送开关或到期时间挡住。
3. `blocked` 先修凭证、账号权限、端点或通道配置；主账本可在停止写进程后执行 `retry`。
4. 遇到 `unknown` 或重启恢复，先核对远端消息/草稿，评估自动重试可能产生的重复；当前没有远端查重接口。
5. 保留失败账本与日志副本；不要删除 JSON、放松共享盘要求或手工改 `delivered` 来掩盖错误。

日志使用通道名、日期、事件 ID、失败次数、错误种类定位问题，不记录 webhook、token 或 secret。无账号的本地 mock 只能证明分类与调度，不证明真实通道有发布权限。

### 8. 配置缺失与权限

缺少已启用通道的必要凭证应在配置阶段失败；运行集合缺少某通道时则按上表执行器规则处理。两者不能合并成同一类“未启用”。微信账号权限、飞书 webhook 权限属于外部服务授权；应用没有用普通用户或管理员登录来替代这些通道凭证。
