# 存储、快照与重放方案

核对基线：`efdb2fb`，2026-10-29。本文按当前源码说明数据库边界、冻结输入与恢复行为，不用旧文档中的 schema 数字推断实际文件版本。

## S｜情境：最新行情可以变，历史报告必须能解释

行情供应商可能修订历史 bar，同一交易日也可能重新生成报告。系统同时保存可替换的最新视图和按内容寻址的冻结输入：网页默认读最新结果，`replay -revision` 则恢复指定报告生成时的输入。

交易日历、实验、市场环境与预测分别落库；通知账本另存 JSON。这些文件属于同一数据根目录，但没有跨文件事务。备份、升级和排障必须按完整运行状态处理，不能只复制 `market.db` 就声称保留了全部研究和投递记录。

## T｜任务：明确每一层的原子性

| 边界 | 必须成立的行为 |
| --- | --- |
| 数据根目录 | 要求 CIFS 时检查挂载类型；共享盘不可用不回退本地 |
| 普通写入进程 | `Store.Open` 持有 `.stock-watcher.lock` 的非阻塞独占锁 |
| 实验写入 | 单独持有 `.experiments.lock`，可与行情进程并行 |
| 单份 JSON | 完整替换；拒绝损坏、超限和未知字段 |
| 单个数据库事务 | 本事务成功则提交，失败则回滚；不扩展成整个同步流程的事务 |
| 冻结输入 | 内容哈希验证，保留供应商原始值与来源；读取时不拼入新行情 |
| 重放 | 指定 revision、参数摘要与原输入齐备，且构建标识匹配后才计算 |

普通 `MarketDB` 连接不自行取得进程锁；生产命令通过外层 `Store` 管理生命周期。测试或嵌入调用方不能把“成功打开数据库”当成已取得单写所有权。

## A｜行动：从初始化到重放

### 1. 根目录和 JSON 写入

[storage.go](../../internal/storage/storage.go) 的 `Open`、`OpenView` 都要求根目录已经存在。显式初始化可调用 `EnsureRoot`：仅 `require_cifs=false` 时允许创建本地目录；要求 CIFS 时必须已有正确挂载。

路径检查拒绝绝对路径、`..`、非规范路径和目录内部符号链接。写入 JSON 需要独占所有权，过程为：

```text
序列化 → 校验大小 → 同目录临时文件 → 文件 fsync → 关闭文件
      → 再查共享盘 → rename → 目录 fsync
```

共享盘不支持目录同步而返回 `EINVAL/ENOTSUP` 时允许继续，文件同步仍必须成功。这里的原子性是读者看到旧文件或新文件，不是 JSON 与数据库一起提交。

`Store` 文档上限为 8 MiB，读取使用严格 JSON decoder 并拒绝尾随第二个 JSON 值；异常不会被当成空状态覆盖。写入尺寸检查针对追加末尾换行前的 JSON，读取限制针对完整文件，调用方不要把边界字节数当可用业务容量。

### 2. SQLite 打开与迁移

主行情写连接使用 `journal_mode=DELETE`、`synchronous=FULL`、外键和 5 秒 busy timeout，单连接运行；只读连接用 `mode=ro`、`query_only=ON`，核对 schema 和必要索引，不为健康探针扫描整库。写连接额外执行 `quick_check`。

`InitMarket` 可建库，普通 `OpenMarket` 在库不存在时要求先执行 `init`。只读打开缺失行情库会返回没有数据库的视图，供调用方决定旧 JSON 兼容或不可用状态；它不创建新库。

当前行情写入口接受已有 schema 2、3、4、5、6，以及新库 0，拒绝 schema 1 和未声明版本。迁移依次经过基础表、分钟、快照、停牌/日历状态和报告索引；整个升级过程由多步组成，不是覆盖所有步骤的一次大事务。

schema 6 的 [review.go](../../internal/storage/review.go) 给 `report_archive` 补 `as_of`、`generated_at`、`schema_version` 与索引。回填从旧 JSON 提取索引字段，保留原始 payload；无法解析的旧条目不被重写或伪造为有效档案。只读连接不能代替写入口完成迁移。

`predictions.db` 的迁移另有规则：低于 3 时清空旧 `model_run`，保留预测/实际值/Kalman 数据，并补 `prediction.inference_ms`。当前 `OpenDB` 没有主行情库同款的未来版本拒绝分支，也不自行做 `Store.Check` 和符号链接校验；生产依赖外层服务的存储约束。不要把主行情库的全部保护概括成每个数据库都自动具备。

### 2.1 `context.db` 保持 schema 1 的新增缓存

市场指数信号在原有 `context_instrument/context_bar/context_sync` 之外增加五张缓存表，没有递增 `user_version`。当前写连接的 `initSchema` 在一个建表事务中执行 `CREATE TABLE IF NOT EXISTS` 并补索引；旧 schema 1 库首次由新版写入口打开时补表，旧日线不迁移、不清空。读连接只核对版本，不会补表。

| 新表 | 键与用途 | 写入边界 |
| --- | --- | --- |
| `context_minute` | `(code,end_unix)`，境内指数原生 5 分钟 | 一次 `SaveMinutes` 保存一个指数窗口 |
| `context_minute_30` | `(code,end_unix)`，境内指数原生 30 分钟 | 独立于 5 分钟表，避免同一结束时间覆盖不同周期 |
| `context_korea` | `(code,trade_date)`，`KOSPI/KOSDAQ` 日线 | 按单指数调用保存，不依赖境内指数元数据 |
| `context_hang_seng` | `(code,trade_date)`，仅 `hkHSI` 日线 | 单独的恒生影子数据，不改正式信号 |
| `context_korea_minute` | `(code,end_unix)`，`KOSPI/KOSDAQ` 分钟 | 前向缓存，独立于韩国日线 |

各 `Save*` 在写前检查可写状态、输入与共享盘，每次调用各自开事务，按键 upsert，保留窗口以外的数据；并不把五类缓存连同 `context_sync` 一起提交。境内分钟表通过外键引用 `context_instrument`，需已有指数元数据。日线使用日期键，分钟使用 Unix 秒；读取截止日分别按上海或韩国时区计算次日零点的排他上界。

新增读取方法先查表是否存在：旧 schema 1 缺少某张可选缓存表时返回空集合，不视作库损坏，也不影响已有日线查询；数据库本身缺失仍返回 `fs.ErrNotExist`。因此，仅检查 `PRAGMA user_version=1` 不能证明分钟、韩国或恒生缓存齐备，升级验收还要查实际表和数据覆盖。

这些缓存供 [指数方向信号](../market-signal.md) 只读研究使用；周期选择与缺数降级见该专题。韩国分钟尚未进入模型，恒生只供下午影子结果。它们没有加入主行情 `report_input` 或 `replay` 冻结链路；新增缓存不会让主报告重放自动获得相应的历史市场信号。

### 3. 日线同步实际分成两次发布

主流程在 [monitor.go](../../internal/monitor/monitor.go)，写边界在 [sync_task.go](../../internal/storage/sync_task.go)：

| 阶段 | 持久化结果 | 后续失败时留下什么 |
| --- | --- | --- |
| 开始任务、逐股检查点 | `sync_task`、`sync_checkpoint` | 可恢复已完成股票；不是已发布推荐 |
| 覆盖率失败 | `CommitMarketData` 保存有效行情和隔离状态，run 为 failed/coverage | 有效行情仍可供只读查询，旧报告保留 |
| 覆盖率通过 | `CommitCollectedData` 发布行情，run 为 running/analyzing | 算法失败不会回滚这批行情 |
| 分析成功 | `CommitAnalysis` 冻结输入、归档报告、替换当前报告和结果、标记 published | 此事务失败则不发布半份新报告 |

`CommitSnapshot` 提供行情与报告一起提交的接口，但不能据它把生产同步写成单次事务。生产先发布行情，再分析；任务心跳和检查点也有独立写入。

报告事务内的 `selection_run` 和 `selection_result` 同时更新。看板通过一致性读事务取得成套快照；单次 API 不应混到旧摘要与新排名。并发一致性必须由运行测试证明，静态 SQL 检查不能替代。

### 4. 最新视图、冻结窗口与 revision

[history_snapshot.go](../../internal/storage/history_snapshot.go) 定义三类标识：

| 标识/表 | 生成与读取规则 |
| --- | --- |
| `history_snapshot.id` | 对历史 JSON 求 SHA-256，gzip 压缩 payload，内容相同则复用 |
| `history_revision` | `(code, adjust, as_of)` 指向当前该日期的窗口快照；同日修订可改变指针 |
| `report_input.id` / `InputID` | 对整批 `SyncItem` 编码求哈希，含调整价、原价、分钟输入、状态证据 |
| `report_archive.id` / `Revision` | 报告先清空 revision 后编码求哈希，再保存带 revision 的 JSON |
| `selection_run` | 按 `as_of` 保存当前展示报告，可以被新 revision 替换 |

`daily_bar` 是最新可替换视图；`history_revision` 也是可更新映射。保持旧报告可重放的是 `report_input` 的完整冻结内容和 `report_archive`，不能把“某日 history_revision 当前指针”当成那天所有历史报告共同的输入。

读取单股快照的解压上限是 8 MiB，报告输入为 256 MiB；解压后核对 SHA-256，再解 JSON。输入中的 `MinuteInputs` 同时接受当前多周期数组和旧单对象，`null` 恢复为空值。该兼容只针对已有表示，不补造缺失分钟线。

报告 revision 校验保留原归档 JSON 的字节顺序，仅移除编码时置于最前面的 revision 字段再验哈希。不能先用新结构解码、重新序列化再计算旧 revision，字段演进可能改变字节流。

### 5. 精排刷新保留原行情输入

[ReplaceReport](../../internal/storage/report_refresh.go) 要求已有日期、目标日和 `InputID` 一致。它创建新的 report revision，保留原输入和旧归档，再在同一事务中替换当前报告与排名结果。

所以“同一 InputID”不意味着“同一 revision”。后续精排补齐或降级状态变化可以产生派生报告；旧 revision 仍能用于回看。通知是否重发由独立账本决定，不由 `ReplaceReport` 触发。

### 6. `replay` 恢复哪些内容

[monitor.Replay](../../internal/monitor/replay.go) 的检查顺序是：

1. 按 64 字符 revision 读取归档，校验报告内容哈希和身份。
2. 要求 `InputID`、provenance、构建标识齐备；旧报告缺这些字段就拒绝重放。
3. 要求当前 `BuildVersion` 与归档的构建标识字符串一致。入口不校验二进制或镜像内容哈希；实际使用匹配制品仍是运维前提，不能把版本字符串相同当作制品一致性证明。
4. 反序列化归档参数并重算 `ConfigDigest`，不一致就拒绝。
5. 恢复冻结调整价、原价及分钟输入，使用原 `GeneratedAt`、`AsOf` 和 `Target` 重新计算。
6. 返回结果并带回原 `InputID/Revision`；不写行情、报告或通知账本。

兼容恢复时，缺少原价的旧输入会按源码回退为调整价；文档不能据此保证所有旧输入都具备独立原价口径。原有算法验证仍可能拒绝不满足输入契约的数据。

此命令不读取后来修订的行情。精排模型尤其需要单独处理：`report_input` 冻结的 `SyncItem` 不包含 `SecondStageModels`；当前 Replay 恢复行情/分钟后没有注入当时的模型快照，`selection.Execute` 可重新读取模型文件。归档安全参数又不含 `DataDir`，恢复后可能从进程相对的 `state/secondstage` 查找模型。因此不能保证还原当时的离线精排分数。重放入口也没有对输出和旧报告作完整逐字段等值断言。验收应比较目标算法的关键结果，不能仅看退出码为 0。

```bash
# 使用归档所记录的同一构建；REVISION 为实际归档的 64 字符标识。
./bin/stock-watcher replay -revision "$REVISION"
```

### 7. 实验与模型文件的独立边界

`experiments.db` 用独立锁保证单实验写进程。保存快照与运行记录使用自己的事务，快照不可变；重新打开写库会把遗留 `running` 标为 `interrupted`、`verdict=pending`，不会自动续跑。实验 JSON 编码上限为 32 MiB，不等于主报告输入的 256 MiB 解压限额。

实时模型保存分多步完成：写 `models/intraday/<model ID>/model.json`、metadata，写 `predictions.db` 的模型记录，再更新当前模型指针。任一步失败都不能宣称模型已经激活；这也不是跨文件原子事务。备份要同时带走数据库、artifact 和指针，保留校验和及特征版本。

市场环境与日内区间的事务只约束各自数据库。跨库读取可能发生在不同时间，消费方必须根据日期、输入截止点和状态判断可用性，不能因共享一个 `data_dir` 就视作同一冻结截面。

### 8. 备份、升级与回滚

备份前停止所有行情、实验、预测和回填写进程，确认连接关闭，再复制完整数据根目录及私有配置。至少覆盖上表数据库、`state/`、`models/` 和 `metadata/listings/`；保留权限与所用二进制/镜像的构建标识。

不得在仍有写入时只拷贝 SQLite 主文件，不得删除 journal 来强行“修复”库。源码使用 DELETE journal，不应在部署中擅自改 WAL。备份目录要与活动共享盘路径区分，恢复验证使用副本。

升级先在副本执行 `init` 和适用迁移，再核对 schema、状态覆盖、报告列表及目标 revision。需要补状态时执行 `status-backfill`，再 `status-audit`；完成后才启动常驻进程。schema 升级失败保留原副本和错误，不用改 `user_version` 冒充成功。

回滚恢复升级前整套备份及匹配构建；只切回旧二进制不能恢复数据库格式。尤其预测 schema 迁移会清理旧模型登记，不宜只回滚模型文件。
