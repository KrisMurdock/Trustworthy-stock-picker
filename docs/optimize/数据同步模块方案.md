# 数据同步模块方案

核对基线：`3e2510b`，2026-10-29。本文描述原生日线同步的现有实现；分钟采集、市场环境同步和消息投递有各自的生命周期。

## S｜情境：行情可用与报告可发布是两个结果

日线同步为看板、策略、初筛和精排提供数据。一轮采集可以保存有效行情，但因为历史完整性或当日可分析率不足，不产生新报告。报告分析失败也不应撤销已经采集成功的行情。

生产入口通过 [CLI](../../cmd/stock-watcher/main.go) 打开存储，再调用 [Monitor.Sync](../../internal/monitor/monitor.go)。`sync` 只采集和生成报告；`run` 启动刷新成功后，才通过调度和投递账本发送消息。`Cycle` 到日线执行时间且没有当日报告时同步，不能用 `once` 替代启动全池刷新。

存储目录必须存在、可写，并由单写进程锁保护。当前 [Defaults](../../internal/config/config.go) 和 [Builtin](../../internal/config/builtin.go) 的 `require_cifs` 都是 `false`；使用共享盘的部署必须显式设置 `STOCK_WATCHER_REQUIRE_CIFS=true`。开启后，不是 CIFS/SMB2 或挂载失效就拒绝写入，没有本地兜底。不能把部署要求误写成内置默认值。

## T｜任务：同步边界和交付条件

| 边界 | 当前契约 |
| --- | --- |
| 日期 | `as_of` 是已完成且在配置日历内的交易日；下一交易日也必须可确定 |
| 数据 | 每个窗口来自一个来源；复权、代码、单位、OHLC、日期和覆盖范围经过校验 |
| 单股失败 | 行情供应商错误可隔离并继续，包括网络失败、限流、单源超时和数据错误；是否发布仍由整池覆盖率决定 |
| 整轮失败 | 调用者取消、整体截止、存储错误和状态证据覆盖不足中止本轮 |
| 完整性 | 不复权历史覆盖上市日与十年前两者中较晚的起点；已知停牌可解释缺 bar，未知状态不能 |
| 发布 | 默认十年完整性至少 95%，当日可分析率至少 90%；两项都达标才分析并保存新报告 |
| 持久化 | 检查点、行情、报告分阶段保存，各写入阶段有自己的事务；不是整轮一个事务 |
| 恢复 | 同日、同配置摘要且未完成的任务可恢复；已完成任务不会被当作未完成任务复用 |

## A｜行动：准备证据、逐股采集、分阶段提交

### 1. 日期、窗口和默认参数

`Sync` 先调用 `validateAsOf` 和 `Calendar.Next`，再建立整体超时。当前默认值如下，环境变量和内部配置入口可覆盖：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `daily.history_days` | 365 天 | 分析窗口长度，按自然日回退 |
| `daily.adjust` | `qfq` | 分析口径 |
| `analysis.sync_timeout` | 90 分钟 | 整轮同步预算 |
| `analysis.timeout` | 10 分钟 | 算法预算，仍受外层同步期限约束 |
| `request_timeout` | 10 秒 | 单请求预算 |
| `market.request_interval` | 1 秒 | 来源客户端节流 |
| `market.attempt_timeout` | 60 秒 | 单来源整窗预算 |
| `market.failure_threshold` / `failure_cooldown` | 3 次 / 5 分钟 | 可重试供应商故障的进程内冷却 |
| `sync.incremental_bars` | 5 根 | 不复权增量请求长度 |
| `sync.status_refresh_days` | 30 天 | 最近状态刷新范围 |

窗口使用以下规则，日期两端均包含；十年前遇 2 月 29 日时夹到 2 月 28 日：

```text
raw_start = max(listed_from, as_of - 10 calendar years)
analysis_start = max(listed_from, as_of - history_days, as_of - 10 calendar years)
if daily.adjust == none:
    analysis_start = raw_start
```

上市日期依次取股池 `listed_from`、已校验的本地缓存和新浪上市资料，见 [listing.go](../../internal/monitor/listing.go)。上市日晚于截止日，不请求价格。元数据源错误可隔离；缓存损坏或读写错误不能作为供应商错误忽略。

### 2. 状态证据是采集前提

[status.go](../../internal/monitor/status.go) 在状态源、交易日历源和数据库都可用时启用状态模式。同步先确保十年交易所日历，再刷新最近状态。首次运行必须先执行 `status-backfill`；普通 `sync` 不会自动回填十年的逐日停牌证据。

最近状态源失败会记录失败并使对应覆盖失效，然后继续刷新其他股票。采集时 `ensureStatusCoverage` 再检查完整窗口；缺证据就返回 `status backfill incomplete`，中止同步。这里与“价格来源失败可隔离”不同，不能统一写成遇到任何上游错误都继续。

有效历史按交易日逐日核对：有 bar 就使用；没有 bar 时只有明确的 `SessionSuspended` 可以解释缺失。`SessionTraded` 但无 bar 记为 `missing_bar`；未知或冲突状态不能冒充停牌。

状态模式允许截止日处于已知停牌：这只股票可以 `Complete=true`，但没有截止日 bar 就是 `Analyzable=false`。因此“最后一根必须等于截止日”只适用于无状态证据的旧校验分支，不能作为所有路径的通则。

### 3. 每只股票分别保存复权与不复权结果

采集前检查取消和数据目录。`collectStockWithEvidence` 先拉分析窗口；只要配置复权不是 `none`，就再拉十年不复权窗口，**不以策略是否开启为条件**。两个窗口之间等待 350ms；发生新采集的股票之间也等待 350ms，缓存复用不走这段等待。

两个窗口各自记录状态：`Status/Reason/Adjusted` 与 `RawStatus/RawReason/Raw`。前复权失败但不复权成功时，仍可保存原始历史并计入完整性。策略启用且分析使用复权价格时，只有复权与原价都可用的股票才进入策略输入；保存数据与进入算法是两层判断。

### 4. 来源回退、隔离和冷却

[Sources.Attempt](../../internal/market/sources.go) 按 `tencent → sina → baostock → tushare → eastmoney` 尝试完整窗口。调用方把日期、复权和覆盖校验放在 attempt 内，因此 HTTP 成功但数据不合格也能回退。

单来源预算超时转换为供应商失败，可以尝试下一个来源；父 context 的取消和整体截止原样返回，禁止继续尝试。可重试网络故障累计到阈值会进入冷却，到期只放行一个恢复探测。数据错误不会被计为整个供应商网络故障。

全部来源失败后，`Monitor` 按 `market.IsProviderFailure` 判断隔离，不再只检查 `IsIsolatable`。所以一只股票的网络/429/5xx 未被备用源恢复，仍会记录隔离原因并继续下一只；只要最终覆盖率达标，剩余有效池可以生成报告。不能把“全部股票都失败时没有报告”的测试，解释为“任何一只网络失败都禁止发布”。

Tushare Token 缺失时跳过该来源；若它是唯一来源，配置校验失败。价格来源顺序不决定上市日期、停牌状态或分钟采集的来源。

### 5. 不复权增量必须证明可合并

只有来源实现 `WindowSource`、数据库已存在、请求为 `none`，且已有历史首根不晚于请求起点，才尝试最近 N 根。合并要求：

- 代码、来源、复权、成交量单位和字段名相同；
- 至少有一个重叠日期；所有重叠 bar 逐字段相同；
- 合并后再次通过窗口校验。

元数据或重叠不一致时改拉完整窗口；增量请求本身返回错误时交给外层来源回退，不保证在同一源再做一次全量请求。前复权窗口每轮完整刷新，不跨轮拼接。

### 6. 恢复与事务边界

[BeginSyncTask](../../internal/storage/sync_task.go) 按 `as_of + fingerprint` 查找未完成任务，加载带摘要校验的股票检查点。采集阶段只复用 `item.Status == ok` 的结果；分析阶段会保留此前冻结的隔离结果。注意这个复用判断检查的是分析侧状态，不是“复权和原价均成功”。

整池遍历结束后，以配置股池总数为共同分母：

```text
coverage_pct   = 100 × count(Complete) / pool_size
analyzable_pct = 100 × count(Analyzable) / pool_size
```

| 阶段 | 存储操作 | 失败后可见结果 |
| --- | --- | --- |
| 采集中 | `CheckpointStock`、任务进度和心跳 | 检查点供恢复；没有半份新报告 |
| 覆盖不达标 | `CommitMarketData` | 保存有效行情、隔离原因和失败运行；不替换旧报告 |
| 覆盖达标 | `CommitCollectedData` | 先发布有效行情，再进入 `analyzing` |
| 分析成功 | `CommitAnalysis` | 保存报告、冻结输入和版本信息，不重新写已发布行情 |
| 分析失败 | 记录失败任务/运行 | 已采集行情保留；下次恢复分析输入 |

[marketdb.go](../../internal/storage/marketdb.go) 在各提交阶段使用 SQLite 事务和写入检查。价格存为百万分之一元整数，原始成交量与股数分别保存。生产 CLI 要求初始化数据库；包内无数据库时仍有旧 JSON 分支，不能把它描述为生产共享盘故障后的备用写入路径。

指数/板块环境通过 `MarketContextSync` 并发执行，股票 `Sync` 返回前等待它结束；环境层失败记日志，不回滚股票行情和报告。它共享本轮 context，不能据此承诺股票命令无需等待环境同步。

### 7. 重建时保留的模块接口

| 边界 | 输入与输出 | 调用方负责 |
| --- | --- | --- |
| `Source.Fetch` | 股票、起止日期、复权 → 一个来源的 `History` | 传入 context 和来源配置 |
| `Sources.Attempt` | 股票、复权、采集校验回调 → 有效窗口或错误集合 | 在回调内执行业务窗口校验 |
| `Monitor.Sync` | 已完成交易日 → 保存后的报告或错误 | 打开存储、写锁与数据库；决定是否入队通知 |
| `MarketDB.Commit*` | `SyncRun`、`SyncItem`、可选报告 → 事务结果 | 按采集/分析阶段调用，不把阶段合成一个长事务 |
